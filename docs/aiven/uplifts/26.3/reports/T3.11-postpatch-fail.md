## Root-cause hypothesis (why the patch is observationally a no-op for this test path)

The patched line at `src/Storages/StorageReplicatedMergeTree.cpp:6722` now reads:

```cpp
if (future_metadata.isPrimaryKeyDefined())
```

`isPrimaryKeyDefined()` (`src/Storages/StorageInMemoryMetadata.cpp:592-595`) returns `primary_key.definition_ast != nullptr`. The patch's premise is that for a table created with only `ORDER BY` (no separate `PRIMARY KEY`), this predicate stays false through the `ALTER`, mirroring the `ReplicatedMergeTreeTableMetadata` ctor rule at `src/Storages/MergeTree/ReplicatedMergeTreeTableMetadata.cpp:80`.

**The premise does not hold.** `AlterCommands::apply` for `MODIFY_ORDER_BY` at `src/Storages/AlterCommands.cpp:653-666` contains:

```cpp
else if (type == MODIFY_ORDER_BY)
{
    auto & sorting_key = metadata.sorting_key;
    auto & primary_key = metadata.primary_key;
    if (primary_key.definition_ast == nullptr && sorting_key.definition_ast != nullptr)
    {
        /// Primary and sorting key become independent after this ALTER so
        /// we have to save the old ORDER BY expression as the new primary key.
        primary_key = KeyDescription::getKeyFromAST(sorting_key.definition_ast, metadata.columns, context);
    }
    sorting_key.recalculateWithNewAST(order_by, metadata.columns, context);
}
```

Trace for the test case (CREATE with `ORDER BY a`, then `ALTER ... MODIFY ORDER BY (a, b)`):

1. `future_metadata = getInMemoryMetadata()` → `future_metadata.primary_key.definition_ast == nullptr` (set to null at CREATE by `registerStorageMergeTree.cpp:695`).
2. `commands.apply(future_metadata, ...)` walks into the `MODIFY_ORDER_BY` branch above. Condition on line 656 is true (`primary_key.definition_ast == nullptr && sorting_key.definition_ast != nullptr`), so `primary_key = KeyDescription::getKeyFromAST(sorting_key.definition_ast, ...)`. `KeyDescription::getKeyFromAST` (`src/Storages/KeyDescription.cpp:90-96`) is a thin wrapper over `getSortingKeyFromAST`; the returned `KeyDescription` has `definition_ast` set to the OLD sorting-key AST (`a`). `MODIFY_ORDER_BY` does NOT then null `primary_key.definition_ast` again, unlike `registerStorageMergeTree.cpp:695` and `AlterCommands.cpp:1320` (in `recalculateColumns`), which both set it back to `nullptr` after the call.
3. By the time the patched line is reached, `future_metadata.primary_key.definition_ast != nullptr`, so `isPrimaryKeyDefined()` returns `true` and the if-branch is taken, writing `future_metadata_in_zk.sorting_key = ...`. `ReplicatedMergeTreeTableMetadata::write` at `ReplicatedMergeTreeTableMetadata.cpp:148-149` then emits `sorting key: ...` because the field is non-empty.

Net: the patched `isPrimaryKeyDefined()` check is observationally equivalent to `true` for any `ALTER MODIFY ORDER BY` on a CREATE-time-no-PRIMARY-KEY table — the same set of cases the old `ast_to_str(...) != ast_to_str(...)` check fired on. The patch is a no-op for the very scenario the dossier (§1) names as the bug. Whatever was being exercised by `93c2be960f...` on the 25.8 branch, the corresponding code path on 26.3 is upstream-divergent in a way that defeats the patch.

(A note on divergence: the dossier's §2 upstream-drift section is correct that no upstream commit modifies the patched line directly. The divergence is upstream of the patched line, in `AlterCommands.cpp`'s `MODIFY_ORDER_BY` handler — which was NOT in the drift scan because the patch does not touch `AlterCommands.cpp`. The drift-scan heuristic "grep for symbols touched by the patch" missed this because `AlterCommands::apply` writes through `primary_key.definition_ast` indirectly via `KeyDescription::getKeyFromAST`, an identifier that did not appear in the patch's text.)
