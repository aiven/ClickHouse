## Root-cause hypothesis (why the redesigned test cannot reach the patched code)

`InterpreterAlterQuery::executeToTable` calls `MergeTreeData::checkAlterIsPossible(...)` (`MergeTreeData.cpp:4445-4452`) *before* it calls the storage's `alter()` method. That function maintains a `columns_in_keys` set populated from the sorting-key, primary-key, partition-key, sampling-key, and TTL expressions of the current metadata. For `AlterCommand::RENAME_COLUMN` it throws unconditionally if the renamed column is in `columns_in_keys`:

```cpp
// src/Storages/MergeTree/MergeTreeData.cpp:4445-4452
if (command.type == AlterCommand::RENAME_COLUMN)
{
    if (columns_in_keys.contains(command.column_name))
    {
        throw Exception(ErrorCodes::ALTER_OF_COLUMN_IS_FORBIDDEN,
                        "Trying to ALTER RENAME key {} column which is a part of key expression",
                        backQuoteIfNeed(command.column_name));
    }
    ...
}
```

For the redesigned test (CREATE with `ORDER BY a`, then `RENAME COLUMN a TO a_new`), column `a` is in the sorting-key expression, so `columns_in_keys.contains("a")` is true and the throw fires before `StorageReplicatedMergeTree::alter` (where the patched line lives) is ever entered. The parent's premise — that `RENAME COLUMN` is the right path because it goes through `AlterCommands.cpp:980-985` and the post-loop fallback at `AlterCommands.cpp:1317-1321` preserves the patch's `primary_key.definition_ast == nullptr` invariant — is technically correct about `AlterCommands` internals, but moot: the ALTER never gets to `AlterCommands::apply` for this scenario.

In other words, the parent's redesigned scenario is **statically impossible** on any current MergeTree-family engine because of `checkAlterIsPossible`, independent of patch 060. To exercise the patched path with `RENAME COLUMN`, the renamed column would have to be NOT in `columns_in_keys` — i.e. a non-sort/non-PK column. But then `RENAME COLUMN` would NOT mutate `sorting_key.definition_ast` (the RenameColumnVisitor only rewrites identifier nodes that appear in the AST), and `setProperties`'s upstream-divergence check (`StorageReplicatedMergeTree.cpp:6722`) would observe `current.sorting_key.definition_ast == future.sorting_key.definition_ast` (or equivalent), so neither the old `ast_to_str(...) != ast_to_str(...)` predicate nor the patched `isPrimaryKeyDefined()` predicate would fire. Result: no `sorting key:` line emitted by either pre- or post-patch — both branches yield `0`, and the test would tautologically PASS without distinguishing the patch.

So this test design has **two mutually exclusive failure modes**: rename a sort-key column → blocked by `checkAlterIsPossible`; rename a non-sort-key column → both pre- and post-patch yield `0` so the test does not exercise the patch differential. There is no third option in which `RENAME COLUMN` both reaches the patched code AND produces different output pre- vs post-patch.

## Mentor note (one observation for the parent)

The parent's test redesign reasoning hinged on `AlterCommands` internals (which branch mutates `primary_key.definition_ast`) but missed that `InterpreterAlterQuery::executeToTable` calls `checkAlterIsPossible` **before** the storage's `alter()` runs, so any test must first pass that pre-storage gate before patch behavior can be observed. A useful drift-scan extension for patches in `StorageReplicatedMergeTree::alter` (or any `IStorage::alter` override) is: list every `throw` in `MergeTreeData::checkAlterIsPossible` that matches the patch's `AlterCommand::Type`, and confirm the test scenario does not trip any of them. For patch 060 specifically, the practical implication is that any `9060_*` stateless test which mutates the sort key on a CREATE-time-no-PRIMARY-KEY table cannot use `RENAME COLUMN` and cannot use `MODIFY ORDER BY` (per T3.11) — the only remaining sort-key-mutation surface is `MODIFY COLUMN <type>` on a sort-key column (which goes through yet another `AlterCommands` branch, `MODIFY_COLUMN`) or `DROP COLUMN` of a non-sort column whose drop somehow re-emits the metadata. Neither has been analyzed against the patched predicate, but both are worth a desk-check before another verification cycle is dispatched.

## Today you learned

- Some ALTER scenarios are rejected by `MergeTreeData::checkAlterIsPossible` (`MergeTreeData.cpp:~4445`) *before* the storage's `alter()` method runs, so a patch inside `StorageReplicatedMergeTree::alter` is observationally inert for those scenarios regardless of correctness.
- For Replicated*MergeTree, the ZK `metadata` znode shape is controlled by `ReplicatedMergeTreeTableMetadata::ReplicatedMergeTreeTableMetadata` (which decides whether `sorting_key` is set) AND by `ReplicatedMergeTreeTableMetadata::write` (which decides whether to emit a `sorting key:` line conditional on the field being non-empty) — patch 060's predicate must align with both.

## Rule of thumb

When patching the body of `IStorage::alter`, validate the test scenario against `MergeTreeData::checkAlterIsPossible` first; if the scenario is rejected there, the test never exercises the patched code regardless of what the patch does.
