## 2. Branch invariants

- Only act (read or write source files) when HEAD is on a `*-aiven-dev` branch.
- Never commit to `master`, `main`, or `v*-aiven` (release-line).
- Do not create arbitrary feature/task branches, and do not `git push`. Work in place on the `*-aiven-dev` branch and stage; the human commits there. (Parallel work, if ever needed, uses a separate git worktree — not a branch.)
- **Sole exception:** if no `*-aiven-dev` branch exists for the current version — e.g. a fresh clone whose HEAD is the release line — you may create *that one branch* off the current HEAD and switch to it, then report that you did so. This is the one case where "do not create branches" and the root `CLAUDE.md` rule "create a new branch for every task" would otherwise deadlock: the `-aiven-dev` branch **is** the task branch for this fork, and every other rule here assumes it exists.
- If you find yourself on any other wrong branch, STOP and report.

### Scoped exception: `contrib/antlr4-grammars*` (granted 2026-09-17)

The PromQL/`TimeSeries` upstream feature port (see
`docs/aiven/plans/2026-09-17-promql-timeseries-backport.md`) must update the ANTLR
PromQL grammar and its checked-in generated parser:

```
contrib/antlr4-grammars/promql/**
contrib/antlr4-grammars-cmake/generated/**   (PromQL* files only)
```

Those files *are* the newer PromQL syntax — quoted identifiers in selectors, quoted and
trailing-comma grouping labels, hexadecimal literals and digit separators, and the
`@ start()` / `@ end()` / `@ <timestamp>` modifiers. There is no way to reach syntax parity
without them, and dropping the dependent features costs
real Prometheus-compliance score.

Terms of the exception:

- It covers **only** the PromQL grammar and the PromQL generated-parser files, and
  **only** content taken verbatim from a pinned upstream commit. Hand-authored grammar
  changes are still forbidden.
- Prefer `git checkout <pinned-upstream-sha> -- <path>` over `Write`/`Edit`. It is the
  same result, it is auditable, and it does not depend on the write hook's disposition.
- The resulting delta (10 files, +948/−748 as measured on 2026-09-17) is an **accepted,
  documented next-LTS rebase conflict**. It must be listed in the effort's dossier so
  whoever does the rebase is not surprised.
- Upstream checks the regenerated parser in, so **no ANTLR run is required** here.

No other `contrib/**` path is in scope. The hook still denies the whole prefix; that is
intentional — the exception is narrow enough that going through `git checkout` is the
right friction.

## 5. Agent does not commit

- Use `git cherry-pick --no-commit` to stage changes from a source commit.
- Use `git add` to stage new files (e.g., a new stateless test).
- DO NOT run `git commit`. The hook denies it.
- Your success state is "everything verified and staged". The human runs
  `git commit` themselves.

## 6. Halt-and-escalate contract

## 7. Tests are required

> **Category (E) upstream feature ports** are governed by the relaxation in
> `docs/aiven/runbooks/commit-hygiene.md` §1(E): for a snapshot port of a subsystem
> upstream already tests, the evidence pair is discharged by the ported upstream tests
> (`tests.added: no_justified`). Aiven-specific behavior in the path set — migration
> compatibility for existing Aiven tables above all — is **not** covered by that
> relaxation and still needs its own test and its own evidence.

Every patch you port MUST satisfy one of:

(a) **A new test that fails on the parent commit and passes after the patch.**
    Default is a stateless test under `tests/queries/0_stateless/`. Integration
    tests are appropriate only when the behavior is genuinely cluster-level.
    Your halt-and-escalate report's Evidence section MUST include both
    command outputs: the pre-patch run showing the test FAIL, and the
    post-patch run showing the test PASS. This is the evidence-of-causation
    pair.

(b) **A documented justification naming an existing upstream test.**
    Acceptable only when the patch is build-system-only, a config rename,
    or upstream behavior is already exercised by a test you identify by
    path. The dossier records the existing test's path; the report sets
    `tests.added: no_justified` and explains.

Aiven patches often gate on shared error codes (`SUPPORT_IS_DISABLED`,
`BAD_ARGUMENTS`, etc.). A test that merely asserts the error code is
insufficient — upstream may throw the same code for unrelated reasons. Your
test must demonstrably distinguish the Aiven gate: use an object/setup that
the Aiven gate rejects but for which the upstream gate (if any) would NOT
fire, and assert both error_code AND a substring of the error message
specific to the Aiven check.

If you cannot design such a test after reasonable effort, escalate with
`test_design_blocked` — silently shipping no test is forbidden.

**Default-behavior changes with broad blast radius.** If a patch would change a
*default* behavior that a broad class of existing objects or queries hit (e.g.
auto-transforming `MergeTree` into `ReplicatedMergeTree`), do NOT ship it on by
default and do NOT try to prove safety by running the whole suite. STOP and
escalate `policy_call`: the human decides whether to gate it behind a new
default-disabled server setting (e.g. `enforce_table_replication`). Test the
gated behavior with the setting explicitly enabled. See clause (v) in
`docs/aiven/skills/dispatch-prompt-template.md`.
